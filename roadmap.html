0.4 Compiling and debugging, every time

gcc -Wall -Wextra -g -o prog prog.c      # always -Wall; it catches most of your bugs
gcc -Wall -g -o prog prog.c -lpthread    # threads (Module 8)
./prog
echo $?                                  # exit status
strace ./prog                            # every system call the program makes

-Wall is not optional advice here. Missing #includes in system programming produce implicit-declaration bugs that silently truncate return values.

The habit that will save you the most time: every system call returns -1 on failure and sets errno. Check it, every time:

#include <stdio.h>
#include <errno.h>
int fd = open("temp", O_RDWR);
if (fd == -1) { perror("open"); return 1; }

perror() prints your string plus the human-readable errno. Half the "my program does nothing" problems in this assignment are an unchecked -1.

02

Computer architecture, kernels, and where Linux sits

vocabulary for everything after

Deck s.4–15. Maps to CO1. No exercises, but this is mid-term material and it is the vocabulary for everything after.

1.1 The machine (s.4–5)

Hardware → kernel → system-call interface → libraries → applications. The kernel owns the CPU, RAM (including virtual memory), and I/O devices; a user process never touches them directly.

Types of system (s.5): Server, Desktop, Embedded, Real Time. Each drives a different kernel design.

1.2 GPOS vs RTOS (s.6, s.8)

  • GPOS (general purpose — Linux, Windows) optimises throughput and fairness. Average response time matters; worst case does not.
  • RTOS optimises determinism. A task must complete within a guaranteed deadline. Soft real time = a missed deadline degrades quality. Hard real time = a missed deadline is a failure.
  • RTOS examples from s.8: VxWorks and RTLinux (Wind River — data acquisition, line cards, core routers), QNX (consumer devices, smartphones), eCos, RTAI, MontaVista. ISRO's Master Controller Facility and Antenna Controller System are named on the slide.

Week 8 of the syllabus is "Implementation of Soft Real Time Systems as per POSIX standard" — that is CO4, and it is what SCHED_FIFO/SCHED_RR in Module 5 are for.

1.3 Kernel architectures (s.7, s.9, s.10)

Monolithic Microkernel Hybrid
What's in kernel space everything: scheduler, VM, FS, drivers, network bare minimum: IPC, scheduling, basic memory core in kernel, some services outside
Services kernel functions user-space servers talking via message passing mixed
Speed fast (no message-passing overhead) slower (context switches per request) in between
Isolation / fault tolerance poor — a driver bug panics the system good — a failed server restarts medium
Used for server and desktop (Linux) embedded and real-time (QNX) both RT and non-RT tasks

Linux is monolithic but modular — drivers load and unload at runtime as kernel modules (that is Module 17).

1.4 Operating system vs kernel

The kernel is the resource manager — one program, always resident. The operating system is the kernel plus shell, libraries, utilities, init system, package manager. "Linux" strictly names the kernel; a distribution (Ubuntu, Fedora, Debian — s.12) is the OS built around it.

1.5 Linux specifics (s.11, s.13, s.14)

  • Started 1991 by Linus Torvalds, released under the GPL (LSS s.2). Sources at kernel.org.
  • uname -r prints your running kernel version; uname -a prints everything.
  • Kernel source layout (s.13): /usr/src/linux-<ver>/ with kernel/ (scheduler, fork, signals), mm/ (memory), fs/ (VFS + filesystems), net/, drivers/, include/linux/ (headers — sched.h lives here, you will meet it in Module 5), arch/ (per-CPU code).
  • Booting (s.14): firmware/BIOS → bootloader (GRUB) → kernel image decompresses and initialises subsystems → mounts the root filesystem → starts PID 1 (init/systemd) → runlevel/target services → login.

1.6 Kernel subsystems (s.15)

Five, and they are exactly the syllabus:

  1. Process management — creation, scheduling, termination (Modules 5–6)
  2. Memory management — virtual memory, paging (Module 16)
  3. File / VFS management — the file abstraction over every device (Modules 2–4)
  4. Device drivers — hardware access (Module 17)
  5. Networking — protocol stacks (Module 15)

Plus IPC cutting across them (Modules 10–15).

Files, filesystems, inodes, links, and /proc

what ls -l is actually telling you

Deck s.16–32. This is the foundation for CO2 and for every question in Set B.

2.1 The inverted tree (s.16)

One rooted hierarchy at /. There are no drive letters — every device is mounted into this single tree. See LBC §2.1 FHS (p.11 / PDF p.19) and man hier (LSS s.4).

2.2 Seven file types (s.17–18) — memorise this table

ls -l output's first character is the type. This is exactly what L1 Q14 asks you to detect in C.

Character devices transfer byte-at-a-time, unbuffered — monitor, keyboard, mouse, tape. Block devices transfer fixed-size blocks through the buffer cache — hard disk, CD-ROM, floppy.

2.3 VFS and the filesystem zoo (s.19–20, s.24)

VFS (Virtual File System) is the abstraction layer that lets open/read/write/lseek/close work identically on ext4, XFS, vfat, iso9660, NFS, and /proc. A process sees one logical filesystem; underneath it may be many physical ones.

From man fs (s.24): minix (the first), ext → ext2 (high-performance, fixed disk and removable) → ext3 (adds journaling) → ext4, ReiserFS (Hans Reiser), XFS (SGI), JFS (IBM), msdos/vfat (Windows), proc (pseudo-filesystem).

The layering on s.20: process → fd table → VFS → concrete FS (XFS / ext4 / proc) → buffer cache → device drivers → physical device.

2.4 Disk layout: boot block, superblock, inode table, data blocks (s.25–27)

When a filesystem is created, the device is divided into:

  1. Boot block — bootstrap code
  2. Superblock — the filesystem's metadata: a bitmap of free/used blocks, the data block size, the count of inode-table entries, and the date/time of the last check. Multiple copies are kept, because a corrupted superblock would make the device unusable; a backup superblock can be used to mount.
  3. Inode table — one entry per file. Its size fixes the maximum number of files the filesystem can ever hold. The inode for / is created automatically.
  4. Data blocks — file contents.

What is in an inode (s.27) — this is precisely L1 Q9:

  • owner UID and GID
  • file type and access permissions
  • timestamps: created/changed (ctime), last modified (mtime), last accessed (atime)
  • size of the file
  • number of hard links
  • pointers to the data blocks

Note what is not in the inode: the filename. Names live in directory entries, which map name → inode number. That is the entire reason hard links work.

sudo dumpe2fs /dev/sda1 | head -40             # s.25
sudo dumpe2fs /dev/sda1 | grep -i superblock

2.5 Indirect blocks and maximum file size (s.21)

An ext inode holds N direct block addresses plus a single indirect, a double indirect, and a triple indirect pointer. With a 4 KB block and 12 direct blocks, the slide's arithmetic is:

12 × 4 KB                        direct
+ 1024 × 4 KB                    single indirect
+ 1024 × 1024 × 4 KB             double indirect
+ 1024 × 1024 × 1024 × 4 KB      triple indirect

which reaches the terabyte range — the slide says up to 16 TB. Be able to reproduce this calculation; it is a classic exam question.

2.6 Kilo vs Kibi (s.22)

Decimal SI: kilo = 10³, mega = 10⁶, giga = 10⁹, tera = 10¹². Binary IEC: kibi = 2¹⁰ = 1024, mebi = 2²⁰, gibi = 2³⁰, tebi = 2⁴⁰. A "1 TB" disk holds 10¹² bytes, which the OS reports as ~0.91 TiB. That gap is the entire marketing controversy.

2.7 Device special files and the switch table (s.28)

A device special file records: device name, type (block or character), major number, minor number. The major number selects the driver; the minor number selects the instance (e.g. major 3 = hard disk, minor 1 = hda1; major 2 = floppy).

The kernel keeps a switch table indexed by major number. The full access chain the deck wants you to be able to recite:

fd  →  file table  →  inode table  →  switch table  →  device driver  →  hardware

ls -l /dev/null /dev/sda /dev/tty       # major, minor printed where size normally is

2.8 Mounting (s.29–30)

Every file lives on a filesystem; every filesystem lives on a device with a device special file. A filesystem must be mounted before use. The mount point is an (ideally empty) directory through which the mounted filesystem's root becomes reachable. /etc/fstab drives boot-time mounts; the root filesystem is mounted by default. When a filesystem is mounted the kernel reads its inode table and superblock into memory.

mount | head
lsblk; blkid                            # named on s.29
cat /etc/fstab

LBC §10.2 (p.60 / PDF p.68) covers mounting a device by hand.

2.9 procfs (s.31) — you will live in here

/proc is a pseudo-filesystem: zero bytes on disk, generated on the fly by the kernel. Three kinds of information: per-process data, system information, system limits.

2.10 Buffer cache (s.32)

Held in non-paged physical memory. Caches everything read from or written to a block device, cutting disk traffic and access time.

On a read miss: allocate a free buffer → read from disk → store in cache. If no buffer is free: the system selects a used buffer, writes it back to disk, marks it free, and allocates it. The requesting process waits throughout. This write-back is why sync() (s.43) exists and why pulling a USB stick without unmounting loses data.

Answer each one in your head — or better, write it down — before opening the answer. Getting one wrong is information, not failure: go back to the section it came from.

01A process opens a file and gets descriptor 3. Why 3, and not 1 or 47?
Show answer

Because the kernel always hands out the lowest free descriptor, and 0, 1 and 2 are already taken — stdin, stdout and stderr are opened for you at process creation.

This is not trivia. It is the mechanism behind dup, behind shell redirection, and behind the pipeline questions in Hands-on List II. close(1) followed by dup(fd) is guaranteed to give you descriptor 1.

02What is the one difference between a hard link and a second copy of a file?
Show answer

A hard link is a second directory entry pointing at the same inode. There is only one file; it now has two names and a link count of 2. A copy is a different inode with different data blocks.

This also explains why hard links cannot cross filesystems — inode numbers are only meaningful within one filesystem.

03Where is a file's name stored?
Show answer

Not in the inode. The inode holds owner, permissions, timestamps, size, link count and block pointers. The name lives in the directory entry, which maps a name to an inode number.

That separation is the entire reason hard links work, and it is a standard exam question.

04mtime and ctime both changed. Then only ctime changed. What did you do?
Show answer

Something that altered the inode but not the contents — chmod, chown, or creating a hard link to the file.

mtime is modification of the data. ctime is change to the inode, which includes data changes but is not limited to them. It is not creation time, despite the name.

05Why does /proc report a size of zero?
Show answer

Because nothing is stored there. procfs is a pseudo-filesystem generated by the kernel on the fly when you read it — the files are views onto live kernel data structures, not blocks on a disk.

06A monolithic kernel is faster than a microkernel. What do you give up for that speed?
Show answer

Fault isolation. In a monolithic kernel every driver and subsystem runs in kernel space, so a driver bug can panic the whole system. A microkernel runs those as user-space servers that can crash and restart — at the cost of message-passing overhead on every request.

That trade-off is why desktops and servers run monolithic kernels and why embedded and real-time systems often run microkernels.

07Your VM has 4 GB of RAM and free -m says almost none is free. Is that a problem?
Show answer

No. Memory holding the buffer cache is instantly reclaimable — Linux uses spare RAM to cache block devices because unused RAM is wasted RAM. The column to read is available, not free.

Deck s.33–43. The single densest and most valuable module in the course. Almost all of CO2 and thirteen of the thirty List 1 questions come from here.

3.1 The I/O model (s.34)

Unix I/O is a sequence of bytes, accessible sequentially or randomly. There are no file formats (no sequential/indexed organisation) and no file control blocks in a user process. Everything is a stream of bytes.

A process refers to a stream by a file descriptor — a small non-negative integer. Facts to know cold:

  • Each process has its own fd table.
  • Descriptors run 0 … a configurable maximum (ulimit -n, /proc/sys/fs/file-max).
  • The kernel pre-opens 0 = stdin, 1 = stdout, 2 = stderr at process creation.
  • The kernel always assigns the lowest free descriptor. This one rule is the engine behind dup, dup2, and every shell redirection — it is how L1 Q11 and LII Q17/Q18 work.
  • A failed open returns -1.

3.2 The five tables (s.35–38) — draw this from memory

process                  system-wide                system-wide

│ fd table │ ─────────► │  file table  │ ────────► │ inode table  │ ─────► │   data   │
│ 0 stdin  │            │  offset      │           │ inode number │        │  blocks  │
│ 1 stdout │            │  mode        │           │ metadata     │        └──────────┘
│ 2 stderr │            │  flags       │           │ block ptrs   │
│ 3 file1  │            │  perms       │           └──────┬───────┘
└──────────┘            │  → inode     │                  │ (device special files only)
                        └──────────────┘                  ▼
                                                   ┌──────────────┐     ┌──────────────┐
                                                   │ switch table │ ──► │ device driver│
                                                   └──────────────┘     └──────────────┘
  • fd table — per-process, just pointers into the file table.
  • file table — holds the file offset, open mode, flags, permissions, and a pointer to the inode entry. Two open() calls on the same file create two file-table entries with two independent offsets; dup() creates two fd-table entries sharing one file-table entry and therefore one offset. This sentence is the answer to half of L1 Q11 and L1 Q22.
  • inode table — in-memory inodes.
  • switch table — for device special files only, indexed by major number.

3.3 How a system call actually executes (s.38–39)

System-call code lives in kernel memory, which a user process cannot address. So the first thing a system call must do is switch to kernel mode. On x86 the wrapper function issues int 0x80 (modern x86-64 uses syscall), which traps into the kernel.

Trace the steps on s.39: push arguments → call the library wrapper read → put the syscall number in a register → trap to the kernel → the system-call handler dispatches through the system call vector table → the kernel routine runs → return to user space → adjust the stack → back in the caller.

Three layers, and the deck wants you to distinguish them:

Layer Examples
Library functions (application programs) fopen, fread, fwrite, fclose
System calls (system programs) open, read, write, close
Driver entry points (kernel programs) my_open, my_read, my_write, my_release

ausyscall --dump lists every system call number. strace ./prog shows the ones your program actually makes.

3.4 The calls themselves (s.40–43)

int creat(const char *file_name, mode_t mode);

int open(const char *file_name, int flags, mode_t mode);

fd = open("temp", O_RDWR | O_CREAT, 0744);

Flag Meaning
O_RDONLY / O_WRONLY / O_RDWR access mode — exactly one, and it is not a bit you can test with &
O_CREAT create if absent; mode argument becomes mandatory
O_EXCL with O_CREAT, fail if the file already exists (returns -1, errno == EEXIST). This is L1 Q4

creat(path, mode) is exactly open(path, O_WRONLY|O_CREAT|O_TRUNC, mode) — write-only. That write-only restriction is the point of L1 Q3.

int read (int fd, void *buf, int count);        // returns bytes read, 0 = EOF, -1 = error
int write(int fd, const void *buf, int count);  // returns bytes written, 0 = nothing, -1 = error
int lseek(int fd, off_t offset, int whence);    // returns new offset, or -1

whence is SEEK_SET (from start), SEEK_CUR (from current), SEEK_END (from end).

Seeking past end-of-file creates a hole — the file's reported size grows, the skipped region reads as zero bytes, and no disk blocks are allocated for it. This is exactly L1 Q10, and od is how you see it.

int new_fd = dup(int old_fd);        // lowest free descriptor
int dup2(int old_fd, int new_fd);    // force a specific descriptor, closing it first if open

Both make the two descriptors share locks, file position, and flags (s.40) — they point at the same file table entry. Note: the deck's slide writes dup2(int new_fd, int old_fd); the actual POSIX order is dup2(oldfd, newfd) — copy old onto new. Use man 2 dup2 as the authority and mention the slide's ordering in your write-up if you want to be thorough.

int select(int n, fd_set *readfds, fd_set *writefds, fd_set *exceptfds, struct timeval *timeout);

Handles more than one descriptor efficiently — it blocks until one is ready or the timeout expires. Macros: FD_ZERO, FD_SET, FD_CLR, FD_ISSET. n must be the highest descriptor number plus one, not the count — the classic bug. Returns the number of ready descriptors, 0 on timeout, -1 on error. This is L1 Q13 and LII Q22.

Internal kernel routines named on s.43, worth knowing for the mid-term: namei() (path → inode), iget()/iput() (read/write an inode), bread()/bwrite() (block from/to buffer cache), getblk() (get a free cache block).

File locking

race conditions, and closing them

Deck s.44–51. Completes CO2. Short module, three questions, and the concepts (race condition, critical section) come back in Module 14 with semaphores.

4.1 Why (s.44)

Multiple processes sharing one file → concurrent access → race condition (the outcome depends on timing) → possible deadlock. The fix is synchronisation, and for files that means file locking.

4.2 Two types (s.45)

Mandatory locking Advisory / record locking
Granularity the entire file a specific byte range
Enforced by the kernel — every read/write is checked cooperating processes only — a process that never asks is never blocked
Cost serialises all access concurrent access to different records
Requires filesystem mounted -o mand, file set chmod g+s,g-x nothing special

4.3 Why record locking wins (s.46)

The slide's arithmetic: five processes each needing 1 second on a different record. Whole-file mandatory locking → they queue → 3 seconds (for the three shown). Record locking → they run concurrently → 1 second. Granularity buys parallelism. Be able to state that trade-off in one sentence.

4.4 struct flock and fcntl (s.47)

struct flock {
    short  l_type;    /* F_RDLCK, F_WRLCK, F_UNLCK */
    short  l_whence;  /* SEEK_SET, SEEK_CUR, SEEK_END */
    off_t  l_start;   /* offset where the lock starts */
    off_t  l_len;     /* how many bytes; 0 = to end of file */
    pid_t  l_pid;     /* filled in by F_GETLK: who holds the conflicting lock */
};

int fcntl(int fd, int cmd, struct flock *);
cmd Behaviour
F_SETLK try to lock; return -1 immediately if blocked (EACCES/EAGAIN) — non-blocking
F_SETLKW lock, W = wait — block until acquired
F_GETLK don't lock; report whether a lock would be blocked, and by which PID

Semantics (s.47): a read lock allows many readers but not one writer (shared). A write lock allows exactly one writer and no readers (exclusive).

Set l_start = 0, l_len = 0 to lock the whole file. l_type = F_UNLCK releases. Locks are released automatically when the fd is closed or the process exits.

Checkpoint

answer before revealing

Answer each one in your head — or better, write it down — before opening the answer. Getting one wrong is information, not failure: go back to the section it came from.

01You open() the same file twice in one process and write through both descriptors. You then dup() a descriptor and write through both of those. Why do the results differ?
Show answer

Two open() calls create two file-table entries, each with its own offset — so the second write starts at zero again and clobbers the first.

dup() creates a second fd-table entry pointing at one shared file-table entry, so the two descriptors share an offset and the writes append cleanly.

That distinction is L1 Q11, and it comes back as L1 Q22 when the second descriptor belongs to a forked child.

02Why does flags & O_RDONLY never work?
Show answer

Because O_RDONLY is 0. The access mode is not a set of bits you can test individually — it is a small enumeration packed into a field.

Mask it out first: flags & O_ACCMODE, then compare against O_RDONLY, O_WRONLY, O_RDWR. Flags like O_APPEND genuinely are bits and do test with &.

03You lseek 10 bytes past the end of a 10-byte file and write 10 more. ls -l says 30 bytes, du says one block. Where did the middle go?
Show answer

Nowhere — it was never allocated. You created a hole. The file's logical size grew, but the kernel allocated no data blocks for the skipped region and synthesises zeros when you read it.

od -c shows the zeros; du shows they cost nothing. This is L1 Q10.

04Why must the first argument to select() be the highest descriptor plus one, rather than the number of descriptors?
Show answer

Because the kernel scans descriptor numbers 0 … n-1 against the bitmask. It is a bound on the range, not a count.

Watching for one descriptor numbered 5 means passing 6, not 1. Also note that Linux modifies the timeval to hold the remaining time, so re-initialise it before every call.

05stat or lstat — which one can tell you a file is a symlink?
Show answer

lstat. stat follows the link and reports on the target, so S_ISLNK can never be true for it.

L1 Q14 asks you to identify any file type, so it has to be lstat.

06Five processes each need one second of exclusive access to a different record in one file. How long does the work take under whole-file locking, and under record locking?
Show answer

Whole-file locking serialises them, so roughly five seconds. Record locking lets them run concurrently on disjoint byte ranges, so roughly one second.

That is the entire argument for granularity, and it is slide 46 of the deck — worth being able to state in one sentence.

07What is the difference between F_SETLK and F_SETLKW?
Show answer

F_SETLK tries, and returns -1 immediately with EACCES or EAGAIN if the lock is held. F_SETLKW — W for wait — blocks until it can acquire it.

There is also F_GETLK, which takes no lock but tells you whether one would block and fills in l_pid with the holder. Printing that PID is cheap marks on L1 Q18.

08A read lock is held on a file. Another process asks for a read lock. Then a third asks for a write lock. What happens to each?
Show answer

The second succeeds — read locks are shared, many readers are allowed. The third blocks — a write lock is exclusive and tolerates neither another writer nor any reader.

Processes: context, structure, states, scheduling

two priority ranges, one scheduler

Deck s.52–67. Start of CO3.

5.1 What a process is (s.53)

A program in execution. It carries a program counter, CPU registers, and a stack holding temporary data. Linux is multiprocessing, and the kernel is reentrant — several processes can be executing kernel code at once.

A process consumes memory, CPU, files. The kernel must track processes and distribute resources fairly. The most important resource is the CPU, and the goal in a multiprocessing environment is maximum CPU utilisation.

5.2 Modes and context switching (s.54)

The hardware must provide at least two modes: kernel mode and user mode. (Intel actually has four rings; Linux uses two.)

Each process has a virtual address space; references are translated to physical addresses through address translation maps (Module 16). Kernel space is a fixed part of every process's virtual address space, mapping kernel text and data structures.

A context switch happens when the running process finishes or blocks on an event: the kernel saves its context, removes it from the running state, and loads the next runnable process's registers.

5.3 Execution context (s.55)

Code Mode Context May access
user code user process process space only
system calls and signals kernel process process space and system space
interrupts, system-wide tasks kernel system system space only

That middle row is why a system call can copy data between your buffer and the kernel — it runs in your process's context. The third row is why an interrupt handler must never touch user memory. Both come back in Module 17 (copy_to_user/copy_from_user).

5.4 task_struct (s.55–56)

Every process is one task_struct, created at fork and destroyed at termination, holding the complete process information. It is large and complex, lives in /usr/src/linux-<ver>/include/linux/sched.h, and the kernel keeps them in a doubly linked list.

5.5 Process states (s.57)

                  ▼

The state constants, which map to the letters in ps/top:

Constant ps letter Meaning
TASK_RUNNING R running or runnable (on the run queue)
TASK_INTERRUPTIBLE S sleeping, can be woken by a signal
TASK_UNINTERRUPTIBLE D sleeping, cannot be interrupted — typically blocked in a device driver. This is why a D-state process survives kill -9

TASK_ZOMBIE Z exited, exit status not yet collected by the parent

The worked example on the slide: $ls → fork() → child → exec("ls") → returns to parent.

5.6 The clock and jiffies (s.58–59)

Every process has a PID — not an index into the task vector, just a number — plus UID and GID used for access control. The kernel tracks creation time and CPU time consumed.

A clock tick is a jiffy; the system clock is a hardware+software combination, independent of CPU frequency. Typical values: 10 ms (100 Hz) or 1 ms (1000 Hz). Interactive responsiveness depends on this frequency.

Each tick the kernel updates the current process's time in user and system mode. Linux also supports process-specific interval timers, single-shot or periodic, which send a signal on expiry (that is Module 7).

5.7 The scheduler's job (s.59–60)

Select the most deserving runnable process from the run queue; avoid starvation; implement a policy; update states every jiffy.

Policies named on the slide: FIFO, Round Robin, Shortest Job First, FILO, priority-based. Scheduling can be pre-emptive or non-pre-emptive.

Two independent priority ranges — know both cold:

1. Nice value — -20 to +19, default 0. Larger nice = lower priority (you are being "nicer" to others). Nice -20 gets the maximum time slice, +19 the minimum. Time slices: minimum 10 ms, default 150 ms, maximum 300 ms.

2. Real-time priority — 0 to 99 by default. All real-time processes outrank all normal processes. Implemented per POSIX.

Policy Class Behaviour
SCHED_FIFO real-time no time slices — runs until it blocks or explicitly yields
SCHED_RR real-time identical to FIFO except it runs only until its time slice is exhausted
SCHED_OTHER normal the standard non-real-time policy

5.8 The internal priority map (s.62–63)

Internally Linux uses 0–139: 0–99 fixed, for real-time, 100–139 dynamic, for normal processes, where 100–139 corresponds to nice -20…+19. In top, a real-time task shows PR as RT or a negative number; a nice -20 normal task shows PR 0, NI -20.

5.9 O(1) scheduler (s.64)

Constant-time selection regardless of process count, using per-CPU runqueues with an active and an expired priority array and a bitmap to find the highest-priority non-empty queue. When the active array empties, the two arrays are swapped. (Reference on the slide: Robert Love, Linux Kernel Development.) Modern kernels use CFS, but O(1) is what the deck examines.

5.12 Time Stamp Counter (s.117)

Taught later in the deck but needed here for Q19. The TSC is a CPU register counting instruction cycles since boot — the most accurate timing method available.

#include <sys/time.h>
unsigned long long rdtsc(void) {
    unsigned long long dst;
    __asm__ __volatile__ ("rdtsc" : "=A" (dst));
    return dst;
}
/* start = rdtsc(); ...job...; end = rdtsc(); printf("%llu\n", end - start); */

```c

include

struct timespec t1, t2; clock_gettime(CLOCK_MONOTONIC, &t1); getpid(); clock_gettime(CLOCK_MONOTONIC, &t2); long ns = (t2.tv_sec - t1.tv_sec) * 1000000000L + (t2.tv_nsec - t1.tv_nsec); ```

the most examined material here

Deck s.68–76. The rest of CO3, and the most-examined material in the course.

6.1 How a command runs (s.68)

You type a command → the shell searches $PATH for the executable → fork() creates a child → the child's image is replaced by the command's executable image via exec → on completion the child returns an exit status to the parent (the shell).

That two-step — fork then exec — is Unix process creation. Study it until you can narrate it.

6.2 The process tree (s.69)

No process is independent. Every process except the initial one has a parent. Processes are not created from nothing — they are copied/cloned from an existing process. Every task_struct keeps pointers to its parent and its children. pstree shows the shape.

Resource-sharing possibilities: parent and children share all, share a subset, or share nothing. Execution: they run concurrently, or the parent waits. Address space: the child is a duplicate of the parent, or a new program is loaded into it.

6.3 fork() (s.70)

pid_t fork(void);

Every statement after fork() is executed by two processes. The return value is the only way to tell which you are:

Return You are
0 the child
> 0 the parent; the value is the child's PID
-1 fork failed (no new process)

The slide's idiom:

if (!fork()) {
    /* child code */
} else {
    /* parent code */
    wait(0);              /* or waitpid(pid, &status, 0); */
}

And the trick question on the slide: printf("Hello fork %d\n", fork()); prints Hello fork 0 (child) and Hello fork <pid> (parent), in nondeterministic order.

6.4 Copy-on-write, zombies, orphans (s.71) — three exam certainties

COW. Linux does not copy the parent's address space at fork. Parent and child share the pages, marked write-protected. On the first write by either, the kernel copies that page. Benefit: the copy is deferred or avoided entirely — which matters enormously because the very next thing a child usually does is exec, discarding the address space anyway.

Zombie. When a child exits it must hand its exit status to the parent. If the parent is busy or suspended and doesn't collect it, the child cannot fully terminate: it keeps a task_struct (for the exit status) but has released everything else. That is the zombie (Z in ps). The parent collects it with wait()/waitpid(), which is called reaping. A zombie cannot be killed — it is already dead; kill the parent and init reaps it.

Orphan. If the parent exits before the child, the child is an orphan and is adopted by init (PID 1, the "grandparent"), which reaps it. An orphan's PPID becomes 1 — that is how you prove it. (On systemd systems the reaper may be a user-level systemd process rather than PID 1; note whichever you observe.)

6.5 The exec family (s.72)

To run a new program in the current process, specify the pathname, the program name, each argument, and (char *)0 / NULL as the last argument.

int execl (const char *path, const char *arg, ...);
int execlp(const char *file, const char *arg, ...);
int execle(const char *path, const char *arg, ..., char *const envp[]);
int execv (const char *path, char *const argv[]);
int execvp(const char *file, char *const argv[]);

All five are library functions; all of them call the single system call

int execve(const char *filename, char *const argv[], char *const envp[]);

Decode the suffixes — this is how you remember them and it is a standard viva question:

Letter Meaning
l arguments passed as a list, ending in NULL
v arguments passed as a vector (char *argv[])
p PATH is searched, so you can pass "ls" instead of "/bin/ls"
e you supply the environment array explicitly

exec does not return on success — the image is replaced. If the line after your exec call runs, the call failed; always follow it with perror("exec").

6.6 The executable image (s.73–74)

high address   ┌──────────────────────┐
               │        Stack         │  grows down: stack frames, return addresses,
               │          │           │  function locals
               │          ▼           │
               │                      │  ← deliberate gap so both can grow
               │          ▲           │
               │          │           │
               │        Heap          │  grows up: malloc'd memory
               ├──────────────────────┤
               │  Uninitialised data  │  BSS — set to zero before execution starts
               ├──────────────────────┤
               │ Initialised R/W data │  initialised, modifiable
               ├──────────────────────┤
               │ Initialised RO data  │  initialised, read-only
               ├──────────────────────┤
low address    │        Text          │  machine instructions, read from the disk file;
               └──────────────────────┘  shared between processes running the same program

The kernel context of a process is maintained separately and is accessible only to the kernel — it holds what the kernel needs to stop and restart the process while others run.

6.7 Daemons (s.75–76)

A daemon starts at system startup, usually from an initialisation script (/etc/rc), frequently spawns other processes to handle service requests, and then waits for an event or performs a task periodically (a cron job). Example: a print server.

Its properties: runs as a background process, is an orphan process, has no controlling terminal, often runs with superuser privileges, and is a process group leader and session leader.

The slide's creation recipe:

int init_daemon(void) {
    if (!fork()) {          /* child continues */
        setsid();           /* new session: detach from controlling terminal, become leader */
        chdir("/");         /* don't hold a mount point busy */
        umask(0);           /* don't inherit file-creation mask */
        /* specify your job */
        return 0;
    } else
        exit(0);            /* parent exits → child is orphaned → adopted by init */
}

Each line earns its place, and you should be able to say why for each one. See also LBC §7.1–7.3 (p.37 / PDF p.45) on services, daemons and the init system.

01A process shows state D in ps and will not die, even with kill -9. Why not?
Show answer

D is uninterruptible sleep — TASK_UNINTERRUPTIBLE — normally blocked inside a device driver.

Signals are delivered when a process next transitions back toward user mode. A process in uninterruptible sleep cannot be woken to take delivery, so even SIGKILL waits. The fix is to wait for the I/O, not to kill harder.

02Nice value -20 and nice value +19. Which one gets more CPU, and which one needs root?
Show answer

Larger nice means lower priority — you are being nicer to everyone else. So -20 gets the maximum time slice (300 ms) and +19 the minimum (10 ms).

Lowering your own priority is free. Raising it needs root, otherwise any user could starve the machine.

03What is the practical difference between SCHED_FIFO and SCHED_RR?
Show answer

SCHED_FIFO has no time slice: a process runs until it blocks or yields voluntarily. SCHED_RR is identical except that it runs only until its slice expires, then goes to the back of the queue at its priority.

Both are real-time and both outrank every SCHED_OTHER process, whatever its nice value.

04sched_get_priority_max(SCHED_OTHER) returns 0. Is that an error?
Show answer

No. SCHED_OTHER has no real-time priority at all. Normal processes are ordered by the nice value, which is a completely separate range. Returning 0 for both min and max is the correct answer.

05fork() has to copy the parent's entire address space. Why is it fast anyway?
Show answer

Copy-on-write. Nothing is copied at fork. Parent and child share the same physical pages, marked write-protected, and the kernel copies a page only when one of them writes to it.

It matters because the usual next thing a child does is exec, which throws the address space away — so the copy is very often avoided entirely rather than merely deferred.

06A zombie process is using no CPU and no memory. Why can't you kill it, and what does clear it?
Show answer

It is already dead. All that remains is a task_struct holding the exit status, kept because the parent has not collected it. Signals have nothing to act on.

It clears when the parent calls wait() or waitpid(). If the parent never will, kill the parent — the zombie is then orphaned, init adopts it, and init reaps it immediately.

07What do the letters in execlp and execve mean?
Show answer

l = arguments as a list ending in NULL. v = arguments as a vector, char *argv[]. p = search PATH, so "ls" works instead of "/bin/ls". e = you supply the environment array.

All five l/v library functions end up calling the single system call execve(). Prove it with strace -e trace=execve.

08Why does the line after a successful execl() never run?
Show answer

Because there is no longer a program there to run it. exec replaces the process image — same PID, same descriptors, entirely new text, data, heap and stack.

So any code after an exec call is the failure path. Always follow it with perror("exec").

09The daemon recipe calls setsid(), chdir("/") and umask(0). What does each one prevent?
Show answer

setsid() — starts a new session with no controlling terminal, so the daemon does not die when the terminal closes and cannot be reached by Ctrl-C.

chdir("/") — stops the daemon holding a directory busy, which would prevent that filesystem being unmounted.

umask(0) — stops an inherited creation mask silently changing the permissions of files the daemon creates.

And the parent's exit(0) is what orphans the child so init adopts it.

The idea that makes this document make sense

There are three kinds of time in this document and keeping them apart is most of the work. Real time is the clock on the wall. User CPU time is time your code spent executing. System CPU time is time the kernel spent executing on your behalf.

A process that calls sleep(10) burns ten seconds of real time and almost no CPU time at all. That single fact decides whether each of the three interval timers ever fires, and it is why one exercise needs a busy loop where another needs pause().

7.1 alarm() (s.115)

unsigned int alarm(unsigned int seconds);

Sets a one-shot alarm that delivers SIGALRM after seconds. Returns the seconds remaining on any previously set alarm (0 if none). alarm(0) cancels. Coarse — whole seconds only, which is exactly why interval timers exist.

7.2 The three interval timers (s.115) — memorise this table

Timer Counts down against Signal on expiry
ITIMER_REAL real (wall-clock) time SIGALRM
ITIMER_VIRTUAL user-mode CPU time consumed by the process (including all its threads) SIGVTALRM
ITIMER_PROF total CPU time — user and system SIGPROF

The distinction is the whole point of LII Q1: a process that sleeps burns real time but no CPU time, so ITIMER_REAL fires and the other two do not.

7.3 getitimer / setitimer (s.116)

int getitimer(int which, struct itimerval *val);
int setitimer(int which, const struct itimerval *new_val, struct itimerval *old_value);

struct itimerval {
    struct timeval it_interval;   /* reload value — 0 means one-shot */
    struct timeval it_value;      /* time until the first expiry — 0 disarms */
};
struct timeval { time_t tv_sec; suseconds_t tv_usec; };   /* seconds + MICROseconds */

Both return 0 on success. it_value is when it first fires; it_interval is what it reloads to afterwards. Set it_interval to zero for a single shot, or equal to it_value for a repeating timer.

7.5 Resource limits (s.118–120)

The OS imposes limits on resources, per process. The shell built-in is ulimit; ulimit -a prints them all.

Option Limit
-c max size of core files
-f max size of files created
-l max memory lockable with mlock()
-n max number of open file descriptors
-s max stack size per process
-u max processes for a single user

Every resource has two limits:

  • Hard limit — the absolute ceiling; a fixed value or unlimited. Only the superuser can raise it, and once lowered it cannot be increased again in that process.
  • Soft limit — the user-settable working value, anywhere from 0 up to the hard limit. Any user may set it. Limits are inherited by children.

ulimit -H / ulimit -S select which; the default is the soft limit.

int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource, const struct rlimit *new_limit, struct rlimit *old_limit);

struct rlimit {
    rlim_t rlim_cur;   /* soft limit */
    rlim_t rlim_max;   /* hard limit — the ceiling for rlim_cur */
};

Threads

a function in execution

Deck s.122–124. Short but examinable, and needed for LII Q34.

8.1 What a thread is (s.122)

"If a process is defined as a program in execution then a thread is a function in execution."

A thread is a sequential flow of control through a program. Creating a thread means specifying a function it will run. Single-threading vs multi-threading.

Each thread has its own:

  1. thread ID (tid)
  2. PC, stack pointer, register set
  3. stack
  4. priority
  5. scheduling policy

Threads within a process share:

  1. the process's instructions (text)
  2. address space and data — globals, heap
  3. open file descriptors
  4. signal handlers
  5. pwd, uid, gid

That sharing table is the single most important thing here: it is why threads are cheap, and why they need synchronisation (Module 14) for anything shared.

8.2 Advantages (s.122–123)

Creation, termination and inter-thread communication are all faster than the process equivalents (no address-space copy, no IPC machinery). Improves application responsiveness, uses multiprocessors efficiently, improves program structure, uses fewer system resources. Even on a uniprocessor it helps: the slide's example is a word processor with separate threads for keyboard input, display, and auto-saving. Other applications: LAN file servers, GUIs, web applications.

8.3 Creating threads (s.124)

#include <pthread.h>

void *thread_func(void *arg) {
    printf("thread id is %lu\n", (unsigned long)pthread_self());
    return NULL;
}

int main(void) {
    pthread_t mythread;
    pthread_create(&mythread, NULL, thread_func, NULL);
    pthread_join(mythread, NULL);
    return 0;
}

Compile with -lpthread — the slide says so, and forgetting it is the number-one failure:

gcc -Wall -g -o thr thr.c -lpthread

The four arguments: (1) address of a pthread_t (typedef'd to unsigned long int), (2) attributes — stack size, scheduling policy, priority; NULL takes defaults, (3) the function the thread runs, (4) the argument to that function; for more than one value, pass a pointer to a struct.

pthread_self() returns the calling thread's ID. pthread_join() waits for a thread — the thread analogue of wait().

Signals

software interrupts

Deck s.125–129. Completes CO3, and LII Q8–Q13 live entirely here.

9.1 What a signal is (s.126)

A software interrupt — "a fundamental method for inter-process communication", used in everything from network servers to media players.

A signal is generated when:

  • an event occurs (a timer expires, an alarm — Module 7)
  • a user quota is exceeded (file size, number of processes — Module 7's rlimits)
  • an I/O device is ready
  • an illegal instruction is encountered
  • a terminal interrupt — Ctrl-C, Ctrl-Z
  • another process sends one — kill -9 <pid>

Every signal is a SIGxxx macro with a corresponding integer. kill -l lists them; man 7 signal documents them.

Delivery: when a signal arrives, the kernel stops the process's execution and forces it to call the signal handler. While a handler is running, a newly arriving signal of the same kind is blocked until the handler returns.

9.2 Signal vs interrupt (s.127)

An interrupt comes from hardware to the kernel (a mouse click, an I/O completion). A signal comes from the kernel to a process. The kernel may generate a signal because of an interrupt or a fault — e.g. an illegal instruction traps to the kernel, which then sends SIGSEGV/SIGILL to the offending process. That direction of flow is the exam answer.

9.3 signal() (s.128)

Three possible dispositions: catch it (your handler), ignore it, or let the default action run.

Two signals can neither be caught nor ignored: SIGSTOP and SIGKILL. (This is the whole point of LII Q13.)

#include <signal.h>
void (*signal(int signum, void (*handler)(int)))(int);
/* practically: signal(SIGINT, my_handler); */

Two reserved handler values:

  • SIG_IGN — ignore the signal
  • SIG_DFL — restore the default action

The slide also asks how a process receives a signal when it is: executing in user mode, executing in kernel mode, not running, in interruptible sleep, in uninterruptible sleep. Answer: it is delivered at the next transition back to user mode; a process in uninterruptible sleep (D) cannot be disturbed at all — which is why kill -9 fails on a D-state process (tie this back to s.57).

Signals you need by name:

Signal Cause Default
SIGSEGV invalid memory reference terminate + core
SIGINT Ctrl-C terminate
SIGFPE arithmetic error, e.g. integer divide by zero terminate + core
SIGALRM alarm() or ITIMER_REAL terminate
SIGVTALRM ITIMER_VIRTUAL terminate
SIGPROF ITIMER_PROF terminate
SIGCHLD child stopped or exited ignored
SIGKILL kill -9 terminate — uncatchable
SIGSTOP Ctrl-Z / kill -STOP stop — uncatchable

9.4 sigaction() (s.129)

"sigaction() is same as signal() but it has a lot of control over a given signal."

int sigaction(int signum, const struct sigaction *act, struct sigaction *oldact);

struct sigaction {
    void     (*sa_handler)(int);
    void     (*sa_sigaction)(int, siginfo_t *, void *);
    sigset_t   sa_mask;      /* signals blocked during the handler */
    int        sa_flags;     /* SA_RESTART, SA_SIGINFO, SA_RESETHAND, ... */
};

oldact stores the previous action (usually NULL).

Why sigaction is preferred over signal — the standard exam answer: signal()'s semantics vary between Unix variants (on some, the handler resets to SIG_DFL after one delivery — a race), whereas sigaction gives you an explicit mask of signals blocked during the handler, explicit flags (SA_RESTART to auto-restart interrupted system calls), and siginfo_t telling you who sent the signal and why.

9.5 kill() (s.129)

int kill(pid_t process_id, int signal_number);
  • positive pid — send to that one process
  • negative pid — send to every process whose group ID equals |pid|
  • kill(pid, 0) sends nothing but tells you whether the process exists and you may signal it

Related: raise(sig) sends to yourself; pause() blocks until any signal arrives.

Handler safety, worth one line in every write-up. Only async-signal-safe functions may be called from a handler. printf is not on that list — it is used everywhere in teaching code (including these assignments) and will work in practice, but the correct primitive is write(1, msg, len). Also make any flag the handler sets volatile sig_atomic_t.

01You set ITIMER_VIRTUAL for 10 seconds and then call sleep(30). What happens?
Show answer

Nothing. The timer never fires and the program exits after the sleep.

ITIMER_VIRTUAL counts down against user-mode CPU time, and a sleeping process consumes none. To make it fire you have to spin — while (1) ; — and it will take more than ten seconds of wall clock to get there if anything else is running.

02Which signal does each interval timer deliver?
Show answer

ITIMER_REAL → SIGALRM. ITIMER_VIRTUAL → SIGVTALRM. ITIMER_PROF → SIGPROF.

ITIMER_PROF counts user and system time, so of the two CPU timers it is always the one that expires first.

03You lower a hard limit with setrlimit and then want it back. Can you?
Show answer

Not as a normal user, and not in that process. A hard limit is a one-way ratchet for anyone except the superuser — you can always lower it, never raise it back.

The soft limit moves freely between 0 and the hard limit. Trying to raise the hard limit unprivileged gives you EPERM.

04A thread and a process each have their own stack. What does a thread have that a process does not share?
Show answer

Threads in one process share the address space — globals, the heap, open file descriptors and signal handlers are common to all of them. Each thread keeps only its own thread ID, registers, stack, priority and scheduling policy.

That sharing is why threads are cheap to create and why they need synchronisation for anything they touch together.

05All three of your threads print the same PID. Is something wrong?
Show answer

No — that is correct. They are one process. getpid() returns the same value in every thread.

What differs is the thread ID: pthread_self() gives the library handle, and syscall(SYS_gettid) gives the kernel's ID, which is what appears in the LWP column of ps -eLf.

06Why is returning normally from a SIGSEGV handler a bad idea?
Show answer

Because the faulting instruction re-executes, faults again, and calls the handler again — forever.

Synchronous fault signals like SIGSEGV and SIGFPE are raised by an instruction that has not completed. Unless the handler fixes the cause, it must exit(). Asynchronous signals like SIGINT are different and can safely return.

07Your program installs a handler for SIGSTOP and it never runs. What went wrong?
Show answer

Nothing went wrong — SIGSTOP and SIGKILL cannot be caught, blocked or ignored. signal() itself returns SIG_ERR with errno == EINVAL, which is the cleanest proof to put in a write-up.

The process stops anyway — state T in ps — and kill -CONT resumes it. Note that SIGTSTP, which Ctrl-Z sends, is catchable.

08Why prefer sigaction() over signal()?
Show answer

Because signal()'s behaviour varies between Unix implementations — on some, the disposition resets to default after one delivery, which is a race.

sigaction() gives you an explicit sa_mask of signals blocked during the handler, flags such as SA_RESTART to restart interrupted system calls, and SA_SIGINFO with a siginfo_t that tells you which process sent the signal.

Getting two processes to agree

Twelve of the twenty-four class hours in this course are inter-process communication, and this is all of it bar sockets. Five mechanisms, each one invented because the previous one could not do something — which is the thread to hold onto as you read.

0 / 11 sections

Work through it in order the first time — the sections build on each other. Ticks are kept between visits.

The thread running through all of this

Each mechanism exists because of a specific limitation in the one before it. Hold that chain and the whole document becomes one argument rather than five unrelated APIs:

Pipes are simple, but only work between related processes. FIFOs fix that with a name in the filesystem, but still have no message boundaries and cannot store data. Sockets, in the next document, are the answer to the one limitation none of these address: they all require both processes to be on the same machine.

System V objects — message queues, shared memory segments, semaphore sets — persist until explicitly removed or the machine reboots. They do not disappear when your program exits.

10.1 Why IPC (s.77)

In a multiprocessing environment processes need to communicate and share resources, and shared resources must be synchronised against concurrent access.

Purposes: data transfer, sharing data, event notification, resource sharing, process control.

The mechanisms, in the order the course teaches them:

  1. Primitive — files, signals
  2. Unnamed pipe
  3. Named pipe (FIFO)
  4. System V IPC — message queues, shared memory, semaphores
  5. Socket programming

10.2 Pipes (s.79–80)

Properties to recite:

  • Half duplex — data flows one way only
  • Data is passed in order (FIFO)
  • Uses a circular buffer with zero buffering capacity in the persistence sense — nothing is stored once read
  • read and write on a pipe are blocking calls
  • On the command line it is |, linking two or more commands: ls -Rl | wc
  • The two ends are a set of two descriptors
  • Only between related processes — parent/child/siblings, because the descriptors must be inherited
int fd[2];
pipe(fd);          /* fd[0] = READ end, fd[1] = WRITE end */
write(fd[1], buf, n);
read (fd[0], buf, n);

Mnemonic: fd[0] = 0 = stdin = read. fd[1] = 1 = stdout = write.

The procedure (s.80): create the pipe → fork → parent sends, child reads (or vice versa) → close the unused ends. Closing unused ends is not tidiness — a reader only sees EOF when every copy of the write end is closed, so forgetting it hangs your program forever. That is the single most common bug in Set J.

10.3 One-way and two-way (s.81–82)

One-way, parent → child: parent closes fd[0], child closes fd[1].

Two-way needs two pipes (s.82) — since a pipe is half duplex. Create fd1 and fd2, four descriptors in play per process:

  • parent closes fd1[0] and fd2[1] → writes on fd1[1], reads on fd2[0]
  • child closes fd2[0] and fd1[1] → writes on fd2[1], reads on fd1[0]

10.4 How the shell builds ls -Rl | grep ^d | wc -l (s.83)

Two pipes, three processes. Each process's stdout is replaced by a pipe's write end and the next process's stdin is replaced by that pipe's read end — done with dup2. Data flows left to right through the kernel.

Pipe advantages: simplest form of IPC; persistence at process level; usable in the shell. Disadvantage: cannot communicate between unrelated processes — which is exactly what FIFOs fix (Module 11).

Opens a process by creating a pipe, forking, and invoking a shell. The mode is "r" (read the command's output) or "w" (write to its input). It is the convenience wrapper around everything on s.79–83.

The slide also covers pread/pwrite: same as read/write but starting from a given offset and without moving the file offset. Return values: bytes transferred; 0 means nothing written (pwrite) or end of file (pread).

a pipe with a name

Deck s.85–87.

11.1 What a FIFO is (s.85)

A FIFO is a pipe with a name in the filesystem. Creation, four ways — and LII Q19 asks for all four:

mknod myfifo p                    # shell command
mkfifo a=rw myfifo                # shell command

int mkfifo(const char *file_name, mode_t mode);            /* library function */
int mknod (const char *file_name, mode_t mode, dev_t dev); /* system call */
mknod("./MYFIFO", S_IFIFO | 0666, 0);

Like a pipe: half duplex, FIFO order, circular buffer, zero buffering capacity. Unlike a pipe:

  • created on a filesystem as a device special file (type p in ls -l — s.18)
  • works between unrelated processes — the fix for the pipe's main limitation
  • reusable
  • persists until the file is deleted

11.2 Using one (s.86)

Once created, a FIFO is accessed with ordinary file system calls — open, read, write, select, close. Process 1 opens it write-only and writes; process 2 opens it read-only and reads.

The blocking rule the slides don't spell out but you will hit within five minutes: open() on a FIFO for reading blocks until a writer opens it, and vice versa. That is not a bug. Use O_NONBLOCK if you need otherwise.

Disadvantages (s.86): data cannot be broadcast to multiple receivers; with several readers there is no way to direct data to a specific one; it cannot store data; it cannot be used across a network; it is less secure than a pipe, since any process with permission can read it; and there are no message boundaries — the data is a byte stream. Those last two limitations are precisely what message queues (Module 12) and sockets (Module 15) exist to fix.

11.3 System limits (s.87)

  • OPEN_MAX — the maximum number of files a single process may have open
  • PIPE_BUF — the maximum amount of data that can be written to a pipe or FIFO atomically; it is the size of the circular buffer

A write of PIPE_BUF bytes or fewer will not be interleaved with another writer's data. Larger writes may be split. On Linux PIPE_BUF is 4096 and the pipe capacity is 65536 bytes — note the difference between atomic write size and total capacity in your write-up. This is LII Q23.

System V IPC and message queues

message boundaries at last

Deck s.88–95.

12.1 System V IPC as a family (s.88)

Pipes and FIFOs do not satisfy many applications' requirements — no stored data, no message boundaries, no networking. System V IPC is implemented as a single unit providing three mechanisms: message queues (MQ), shared memory (SHM), semaphores (SEM).

Key property: System V IPC objects persist until explicitly deleted or the system reboots — not until the creating process exits. Forgetting to remove them is how you end up with a system full of orphaned queues. ipcs shows them; ipcrm removes them.

12.2 Common attributes (s.89)

Every IPC object has: key, id, owner, permission, size. Plus per-type:

  • message queue — used bytes, number of messages
  • shared memory — size, number of attaches, status
  • semaphore — number of semaphores in the set

The struct ipc_perm holds the common attributes (uid, gid, cuid, cgid, mode, key).

The key. The first step is a shared unique identifier, a number. Generated with:

key_t ftok(const char *filename, int id);

ftok combines the inode of an existing file with a project id byte. Both processes must call ftok with the same existing path and same id to get the same key — if the file doesn't exist you get -1.

12.3 The uniform API shape (s.90)

Every System V mechanism follows the same three-function pattern, with xxx = msg, shm, or sem:

int xxxget(key_t key, int xxxflg);                        /* id, or -1 */
int xxxctl(int xxxid, int cmd, struct xxxid_ds *buffer);  /* 0, or -1  */

Three ways to obtain a key: from ftok, by choosing a static positive integer, or by using IPC_PRIVATE (a private object only relatives can inherit).

Flags for the get function: IPC_CREAT and IPC_EXCL, OR'd with an access permission — msgget(key, IPC_CREAT | 0744).

Commands for the ctl function:

Command Effect
IPC_STAT copy the object's xxxid_ds structure into your buffer
IPC_SET write permissions/uid/gid back from your buffer
IPC_RMID remove the object

Learn this table once and it covers Modules 12, 13, and 14.

12.4 Message queues (s.91–94)

A message queue overcomes the FIFO's limitations: it stores data and it sets message boundaries. Lifecycle: create the queue → send messages → any process with permission retrieves them → remove the queue. Messages are read from the head, added at the tail.

struct msgbuf {          /* the standard structure */
    long mtype;          /* message type — MUST be first, MUST be > 0 */
    char mtext[1];
};

struct My_msgQ {         /* your own is allowed, as long as mtype is first */
    long  mtype;
    char  mtext[1024];
    void *xyz;
};

int     msgget(key_t key, int msgflg);
int     msgsnd(int msqid, const void *msgp, size_t msgsz, int msgflg);
ssize_t msgrcv(int msqid, void *msgp, size_t msgsz, long msgtype, int msgflg);
int     msgctl(int msqid, int cmd, struct msqid_ds *buf);

msgsz is the size of mtext only — not including the long mtype. Getting that wrong is the classic EINVAL.

The msgtype argument of msgrcv (s.93–94) — this is LII Q27:

msgtype Retrieves
0 the first message, FIFO order
positive the first message of exactly that type
negative the first message whose type is ≤ the absolute value, lowest type first

msgflg of IPC_NOWAIT makes msgrcv return -1 with ENOMSG instead of blocking when nothing matches. msgrcv returns the number of bytes copied into mtext.

12.6 Limitations (s.95)

Effective for small amounts of data; very expensive for large transfers. Each transfer copies the message from the user buffer into a kernel buffer and back — two copy operations per message, which hurts performance. And a message in a queue cannot be reused. This is exactly the argument for shared memory (Module 13), which needs no intermediate kernel buffer.

Shared memory

fastest, and least safe

Deck s.96–100.

13.1 Why (s.96–97)

The fastest IPC mechanism, very flexible and easy to use. Used for global variables, shared libraries, word processors, multiplayer gaming, HTTP daemons.

Faster than semaphores or message queues because it does not require an intermediate kernel buffer — contrast with the two copies per message of s.95. Once the segment is set up it is manipulated exactly like any other memory area: plain pointer reads and writes, no system calls at all.

The five steps (s.97):

  1. Create the shared memory
  2. Connect to it and obtain a pointer
  3. Read / write, and change access mode
  4. Detach
  5. Delete the segment

13.2 The calls (s.98–100)

int   shmget(key_t key, int size, int shmflg);           /* shmid, or -1 */
void *shmat (int shmid, void *shmaddr, int shmflg);      /* pointer, or (void*)-1 */
int   shmdt (const void *shmaddr);                       /* 0, or -1 */
int   shmctl(int shmid, int cmd, struct shmid_ds *buf);  /* 0, or -1 */

shmid = shmget(key, 1024, IPC_CREAT | 0744);

printf("SHM contents : %s\n", data);        /* read — just a pointer */
scanf(" %[^\n]", data);                     /* write — just a pointer */

shmctl(shmid, IPC_RMID, NULL);
  • shmaddr = (void *)0 lets the kernel choose the attach address — always do this.
  • shmflg of SHM_RDONLY attaches read-only; otherwise 0.
  • shmat fails with (void *) -1, not NULL. Check for the right value.

13.3 The race condition (s.100)

"Since many processes can access the shared memory, any modification done by one process in the address space is visible to all other processes. Since the address space is a shared resource, the developer should implement a proper locking mechanism to prevent the race condition."

Shared memory gives you no synchronisation whatsoever. That is the price of its speed, and it is the reason Module 14 exists — LII Q32(b) is exactly "protect shared memory from concurrent write access".

The slide also poses "Data can either be read or written only. Append?" — the answer is that you must track your own write offset inside the segment, because a shared memory segment has no file offset the way a file does.

Semaphores

putting the safety back

Deck s.101–103.

14.1 What (s.101)

A synchronisation tool: an integer counter with two operators, P() and V(), that avoids busy waiting. Used to protect a shared memory segment, a message queue, or a file.

14.2 P and V (s.102)

A process that wants the shared object locks it by asking the semaphore to decrement the counter. If the counter is > 0 the decrement succeeds; otherwise the process waits until it becomes possible.

int p(int i) {              /* wait / lock / down */
    if (i > 0) i--;
    else       wait_until(i > 0);
    return i;
}
int v(int i) {              /* signal / unlock / up */
    i = i + 1;
    return i;
}

Mnemonic: P = proberen (to test) = down = lock. V = verhogen (to increment) = up = unlock.

Binary semaphore (initial value 1) = mutual exclusion, one holder at a time. Counting semaphore (initial value N) = up to N concurrent holders, for a pool of N identical resources.

System V provides a semaphore set — a number of semaphores managed as one unit, the count chosen by you. The kernel performs the operations atomically, which is the entire reason you cannot write this yourself with an ordinary integer.

14.3 The implementation (s.103)

union semun {
    int                 val;    /* value for SETVAL */
    struct semid_ds    *buf;    /* buffer for IPC_STAT, IPC_SET */
    unsigned short int *array;  /* array for GETALL, SETALL */
};

You must define union semun yourself — glibc does not provide it, despite it appearing in every man page. Copy the four lines above into your program.

union semun arg;
semid = semget(key, 1, IPC_CREAT | 0744);
arg.val = 1;                        /* 1 = binary; > 1 = counting */
semctl(semid, 0, SETVAL, arg);      /* semaphore number 0 in the set */

struct sembuf {
    short sem_num;   /* which semaphore in the set; 0 = the first */
    short sem_op;    /* < 0 = lock (P), > 0 = unlock (V), 0 = wait for zero */
    short sem_flg;   /* 0, SEM_UNDO, IPC_NOWAIT */
};

struct sembuf buf = {0, -1, 0};     /* P: add -1 to the current value */
semid = semget(key, 1, 0);
semop(semid, &buf, 1);              /* locked */
/* ---------- critical section ---------- */
buf.sem_op = 1;
semop(semid, &buf, 1);              /* unlocked */

SEM_UNDO is worth using and worth mentioning: it makes the kernel reverse the operation automatically if the process dies while holding the lock. Without it, a crash inside the critical section leaves the semaphore locked forever.

semctl commands: SETVAL, GETVAL, SETALL, GETALL, GETNCNT, IPC_STAT, IPC_SET, IPC_RMID.

Checkpoint

answer before revealing

Answer each one in your head — or better, write it down — before opening the answer. Getting one wrong is information, not failure: go back to the section it came from.

01Your reader blocks forever on a pipe even though the writer finished. Why?
Show answer

Because some copy of the write end is still open — almost always in the parent, which created the pipe and never closed its own descriptors.

read() returns 0 only when every write descriptor is closed. This is the single most common bug in the pipe exercises, and it is also why the parent in a two-child pipeline must close both ends before waiting.

02Explain how close(1); dup(fd[1]); redirects standard output.
Show answer

Closing 1 frees descriptor number 1. The kernel always allocates the lowest free descriptor, so the very next dup() is guaranteed to return 1.

Now descriptor 1 refers to the pipe's write end, and anything the process — or the program it execs — writes to stdout goes into the pipe. That is precisely what a shell does when it sees |.

03A pipe and a FIFO behave identically once open. What can a FIFO do that a pipe cannot?
Show answer

Connect unrelated processes. A pipe's descriptors can only be inherited across fork(), so both ends must be relatives. A FIFO has a pathname, so any process with permission can open it — you can talk to one end with cat from a terminal.

It is also reusable and persists until deleted, whereas a pipe vanishes with its last descriptor.

04You open a FIFO for reading and your program hangs before reaching select(). What is happening, and what fixes it?
Show answer

open() on a FIFO blocks until a writer opens the other end. That is defined behaviour, not a bug.

Pass O_NONBLOCK to the open, which is exactly what LII Q22 needs — otherwise you never get as far as the select() whose timeout the question is about.

05PIPE_BUF is 4096 and a pipe holds 65536 bytes. What are these two numbers?
Show answer

PIPE_BUF is the largest atomic write. A write of that size or less will not be interleaved with another writer's data. The capacity is how much unread data the buffer can hold before a writer blocks.

The slide describes PIPE_BUF as the buffer size, which is the usual simplification — noting the real distinction is worth a mark.

06Two processes call ftok(".", 'a') from different directories. Do they get the same key?
Show answer

No. ftok combines the inode of the named path with the project byte, so the same path string in two different working directories gives two different keys — and two processes that never find each other.

Use an absolute path both sides, and make sure the file exists: if it doesn't, ftok returns -1.

07Why is a message queue described as expensive for large transfers?
Show answer

Because every message is copied twice — from your buffer into a kernel buffer on send, and out of the kernel buffer into the receiver's buffer on receive.

Shared memory has no intermediate kernel buffer at all, which is why it is the fastest mechanism and why message queues are reserved for small, structured messages.

08What do the three values of msgtype in msgrcv do?
Show answer

0 — the first message in the queue, FIFO order. Positive — the first message of exactly that type. Negative — the first message whose type is less than or equal to the absolute value, lowest type first.

That last one gives you a priority queue for free, and it is the interesting half of LII Q27.

09You attach shared memory with SHM_RDONLY and write through the pointer. What do you get back?
Show answer

Not a return code — a SIGSEGV. The page is mapped read-only in your address space and the MMU enforces it in hardware, so there is no error value to check.

Catching that signal with a handler so the program reports the violation instead of dumping core is the strongest possible answer to LII Q30(b).

10A process dies holding a binary semaphore. What happens to everyone waiting, and what prevents it?
Show answer

They wait forever — the semaphore is still at zero and nothing will ever increment it.

SEM_UNDO in sem_flg tells the kernel to reverse the operation automatically if the process dies. Demonstrating the hang without it and the recovery with it is worth more than any amount of working code.

15.1 The stack (s.104)

 user process   │  Application (telnet / ftp)      ← application details
────────────────┼──────────────────────────────────
                │  Sockets                          ← the API boundary
     kernel     │  Transport:  TCP  |  UDP
                │  Network:    IP                   ← communication details
                │  Device driver and hardware

A socket communicates between different machines (different IP addresses). SOCK_STREAM sockets are full-duplex byte streams — note the contrast with pipes and FIFOs, which are half duplex.

15.2 Client–server (s.105–106)

A socket is a communication endpoint, an abstract object a process uses to send or receive messages. The two prevalent APIs on Unix are Berkeley Sockets and System V TLI.

Why sockets rather than plain file I/O (s.106): the client–server relationship is not symmetrical; a connection may be connection-oriented or connectionless; more parameters are needed than for file I/O; Unix I/O is stream-oriented; and the interface must support multiple protocols.

int socket(int domain, int type, int protocol);   /* socket descriptor, or -1 */
Argument Values
domain (address family) AF_UNIX — UNIX domain (same machine) · AF_INET — Internet domain
type SOCK_STREAM — TCP, connection-oriented · SOCK_DGRAM — UDP, connectionless
protocol usually 0; numbers are listed in /etc/protocols

15.4 Addresses and byte order (s.108–109)

struct sockaddr_in {
    short int          sin_family;   /* AF_INET */
    unsigned short int sin_port;     /* port number */
    struct in_addr     sin_addr;     /* IP address */
};
struct in_addr { unsigned long s_addr; };   /* the four-byte IP address */

Endianness. Little endian (Intel) stores the low-order byte at the lower address; big endian (IBM 370, Motorola) stores the high-order byte first. The slide's example: 91,329 = hex 00 01 64 C1, laid out in opposite orders on the two architectures.

Internet protocols use big endian, called network byte order. Convert with:

Function Meaning
htons() host to network short — use for port numbers
htonl() host to network long — use for IP addresses
ntohs() network to host short
ntohl() network to host long

Forgetting htons() on the port is the classic socket bug: the connection silently goes to the wrong port.

15.5 The remaining calls (s.109–112)

int bind   (int sockfd, struct sockaddr *my_addr, int addrlen);
int connect(int sockfd, struct sockaddr *serv_addr, int addrlen);
int listen (int sockfd, int backlog);
int accept (int sockfd, void *addr, int *addrlen);
int shutdown(int sockfd, int how);
  • bind — attach the socket to an IP address and port. addrlen = sizeof(struct sockaddr).
  • listen — converts an unconnected socket into a passive socket, telling the kernel to accept incoming connection requests. backlog is the number of connections allowed on the incoming queue; it should never be zero, since servers always expect connections.
  • accept — returns a new socket descriptor for this one client; the original keeps listening. Set addrlen to sizeof(struct sockaddr_in) before passing its address.
  • close(sockfd) — prevents further reads and writes; the remote end gets an error on further access.
  • shutdown(sockfd, how) — finer control than close: 0 further receives disallowed, 1 further sends disallowed, 2 both.

15.6 The two skeletons (s.113)

/* ---------- SERVER ---------- */                /* ---------- CLIENT ---------- */
struct sockaddr_in serv, cli;                     struct sockaddr_in serv;
sd = socket(AF_INET, SOCK_STREAM, 0);             sd = socket(AF_INET, SOCK_STREAM, 0);
serv.sin_family      = AF_INET;                   serv.sin_family = AF_INET;
serv.sin_addr.s_addr = INADDR_ANY;                serv.sin_addr.s_addr = inet_addr("server ip");
serv.sin_port        = htons(portno);             serv.sin_port = htons(portno);
bind(sd, &serv, sizeof(serv));
listen(sd, 5);
nsd = accept(sd, &cli, &clilen);                  connect(sd, &serv, sizeof(serv));
read/write(nsd, ...);                             read/write(sd, ...);

INADDR_ANY means "bind to every local interface".

15.7 Iterative vs concurrent servers (s.114)

Iterative — one client at a time:

nsd = accept(sd, &cli, &len);
while (1) { read/write(nsd, ...); }

Concurrent — many clients served simultaneously:

while (1) {
    nsd = accept(sd, &cli, &len);
    if (!fork()) {
        close(sd);                /* child doesn't need the listening socket */
        read/write(nsd, ...);
        exit(0);
    } else
        close(nsd);               /* parent doesn't need this client's socket */
}

Both close calls are mandatory. If the child keeps sd, the listening socket never really closes; if the parent keeps nsd, descriptors leak and the connection never fully terminates. Also reap the children (SIGCHLD handler with waitpid, Modules 6 and 9) or you accumulate zombies — a real server bug with a name.

The thread version, for LII Q34(b): replace fork() with pthread_create() running a per-client function (Module 8). Compare: threads are cheaper and share memory, but one crash kills the whole server; processes are isolated but heavier.

Memory management

mid-term only, no exercises

Deck s.130–144.

16.1 Virtual memory (s.131)

Every process gets its own virtual address space, translated to physical memory through page tables. This gives isolation (one process cannot address another's memory), the illusion of more memory than exists, and the freedom to place pages anywhere physical.

16.2 Allocation (s.132–133)

Static allocation — text, initialised data, BSS; sized at compile time, laid out at load time (s.73's image). Dynamic allocation — heap via malloc/brk/mmap, stack frames on call. The gap between heap and stack (s.74) lets both grow.

16.3 Page tables and translation (s.134, s.137, s.139, s.141)

A virtual address splits into page number + offset. The page number indexes the page table, which yields a frame number; the frame plus offset is the physical address.

x86-64 uses a four-level hierarchy (s.141) — PGD → PUD → PMD → PTE → page. Hierarchy exists because a flat table for a 48-bit address space would be absurdly large; with a hierarchy, unused regions need no tables at all.

The TLB caches recent translations so most accesses skip the walk entirely. A miss walks the table; a page fault means the page isn't resident and the kernel must fetch it (demand paging).

Minor fault — the page is in memory, just not mapped (e.g. a COW page, s.71). Major fault — must come from disk. These are ru_minflt and ru_majflt from s.121.

16.4 x86-64 layout and kernel structures (s.136, s.138)

User space low, kernel space high, with a large non-canonical hole between. Kernel structures: mm_struct (the address space, hanging off task_struct), vm_area_struct (one per contiguous mapping — text, data, heap, stack, each mapped file).

16.5 Memory mapping (s.135)

mmap() maps a file (or anonymous memory) into the address space, after which file access is just pointer dereferencing and page faults do the I/O. This is how shared libraries load, and it is the modern alternative to the System V shared memory of Module 13 (shm_open + mmap, the POSIX API).

16.6 free -m (s.143)

free -m

The column that matters is available, not free: memory used by the buffer cache (s.32) is instantly reclaimable, so a healthy Linux system always looks "full". Explaining that is a standard interview question as much as an exam one.

16.7 Walk through program execution (s.144)

Tie it all together and be able to narrate it: shell forks (COW, s.71) → execve (s.72) → kernel tears down the old address space and builds vm_area_structs for the new image (s.73) → the dynamic linker maps shared libraries → the first instruction faults → demand paging brings in pages → the heap grows via brk/mmap on malloc → exit releases the address space, leaving a zombie until the parent reaps it.

17.1 Classification (s.148–150)

Character drivers (byte stream, no buffer cache — terminals, mice), block drivers (fixed-size blocks through the buffer cache — disks), network drivers (packets, no file abstraction). Ties back to s.17–18 and s.28.

17.2 Kernel modules vs applications (s.152–154)

Exit return/exit() cleanup_module() / module_exit()

Library glibc kernel API only — no libc, no printf (use printk)

Namespace pollution (s.154) — a module's symbols enter the single global kernel namespace, so everything not exported must be static and public names need a prefix. There is no linker to isolate you.

17.3 Major and minor numbers (s.155–156, s.180)

The major number selects the driver, the minor selects the device instance — the switch table of s.28. Register with register_chrdev(); create the device file with mknod /dev/mydev c <major> <minor> — the same mknod you used for FIFOs in Set K, with c instead of p.

17.4 file_operations and data transfer (s.168–178)

struct file_operations maps the system calls of Module 3 onto your driver's functions: .open, .release, .read, .write, .llseek, .unlocked_ioctl. That is the third layer of s.38 (my_open, my_read, my_write, my_release) made concrete.

Because user and kernel address spaces are separate (s.55), a driver must not dereference a user pointer. It uses:

copy_to_user(void __user *to, const void *from, unsigned long n);
copy_from_user(void *to, const void __user *from, unsigned long n);

Both return the number of bytes not copied — zero means success.

01What does listen() actually do, given that accept() is what returns a connection?
Show answer

It converts an unconnected socket into a passive one — telling the kernel that this socket should accept incoming connection requests rather than initiate them, and sizing the queue of pending connections with backlog.

The three-way handshake then completes in the kernel before accept() is ever called; accept() just removes a finished connection from that queue.

02accept() returns a new descriptor. What is the original one for now?
Show answer

Still listening. The original socket keeps accepting further connections; the new descriptor is this one client's conversation.

That is what makes a concurrent server possible: hand the new descriptor to a child or a thread and immediately go back to accept().

03Why must the port number go through htons()?
Show answer

Because Internet protocols use big-endian ordering — network byte order — and Intel and ARM are little-endian. Without the conversion the bytes are reversed and your connection quietly goes to the wrong port.

htons for ports (short), htonl for addresses (long).

04In the fork-based concurrent server, why does the child close sd and the parent close nsd?
Show answer

Because fork() duplicates the descriptor table, so both processes hold both descriptors. Each closes the one it does not need.

If the parent keeps nsd, the client's connection never fully closes when the child finishes. If the child keeps sd, the listening socket stays open in processes that have no business listening. And without reaping children on SIGCHLD, the server accumulates zombies.

05A thread-based server passes &nsd to every thread. What goes wrong?
Show answer

Every thread reads the same variable, which the next accept() has already overwritten — so two threads end up serving the same client and one connection is dropped.

Threads share the address space, which is the whole point of them and the whole danger. Pass a malloc'd int, and free it in the thread.

06What is a page fault, and what is the difference between a minor and a major one?
Show answer

A page fault is the trap taken when a virtual address has no valid translation in the page table.

A minor fault is resolved without touching the disk — the page is already in memory and only needs mapping, as with a copy-on-write page after fork(). A major fault requires reading from disk, and is thousands of times more expensive. getrusage counts both as ru_minflt and ru_majflt.

07Why does x86-64 use a four-level page table rather than one flat table?
Show answer

Because a flat table for a 48-bit address space would be enormous and almost entirely empty. A hierarchy means unused regions need no tables at all — you only allocate the levels for address ranges that are actually mapped.

The TLB then caches recent translations so most memory accesses skip the walk entirely.

08Why can a device driver not simply dereference a pointer a user process handed it?
Show answer

Because the driver runs in kernel mode but with a user pointer that may be invalid, unmapped, or deliberately hostile. Dereferencing it directly is a kernel bug that becomes a panic or a security hole.

The kernel provides copy_to_user() and copy_from_user(), which validate the address and handle a fault safely. Both return the number of bytes not copied — zero means success.

09What does the major number in a device file select, and what does the minor select?
Show answer

The major number selects the driver, through the kernel's switch table. The minor number selects which device that driver is being asked about.

It is the same mknod you used to create a FIFO, with c or b instead of p — which is the neatest illustration of why everything in Unix is a file.
